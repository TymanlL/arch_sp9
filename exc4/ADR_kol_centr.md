### **Решение**
Приведите диаграммы контекста и контейнеров в модели C4. Опишите там основные компоненты и интеграции всех элементов решения.

*Примечание: диаграммы представлены в отдельных файлах context-diagram-kc.xml и container-diagram-kc.xml*

#### Описание решения:

1. **Интеграция с системой кол-центра банка**:
   - Разработка нового API в системе ставок АБС для предоставления актуальных ставок по депозитам
   - Разработка модуля в системе кол-центра для получения данных через API и отображения их сотрудникам
   - Использование существующей инфраструктуры и сети банка для безопасного взаимодействия

2. **Интеграция с системой партнерского кол-центра**:
   - Развертывание SFTP-сервера в DMZ-сегменте сети банка для безопасного обмена файлами
   - Разработка модуля в системе ставок АБС для периодического формирования файлов со ставками и их выгрузки на SFTP
   - Настройка системы партнерского кол-центра для периодического получения файлов с SFTP и загрузки данных в свою систему

3. **Процесс обмена данными**:
   - Система ставок АБС выступает источником данных о ставках для обеих интеграций
   - Обновление данных о ставках в системе кол-центра банка происходит через API-вызовы по расписанию (каждые 10-15 минут)
   - Обновление данных в партнерском кол-центре происходит через обмен файлами по SFTP (каждый час)
   - Файлы шифруются перед передачей для обеспечения безопасности

4. **Логика выбора решения**:
   - Для кол-центра банка выбран API-подход, так как обе системы находятся во внутренней сети банка, что обеспечивает быстрый и безопасный обмен данными
   - Для партнерского кол-центра выбран файловый обмен через SFTP, так как:
     - Внешняя система партнера не имеет возможности делать API-вызовы в банк
     - SFTP - стандартный и безопасный протокол для обмена файлами
     - Требования к актуальности данных менее строгие (до 1 часа)
   - Оба метода интеграции минимизируют изменения в существующих системах

### **Альтернативы**
Опишите здесь наиболее важные альтернативные решения.

1. **Единый API Gateway для обоих кол-центров**
   - Преимущества: унифицированный интерфейс, централизованное управление доступом
   - Недостатки: партнерский кол-центр не имеет возможности делать API-вызовы, необходимость открытия доступа к API из внешней сети повышает риски безопасности

2. **Прямая интеграция системы партнерского кол-центра с базой данных АБС**
   - Преимущества: более свежие данные, отсутствие дополнительных компонентов
   - Недостатки: серьезные риски безопасности, нарушение принципа изоляции данных, противоречие корпоративным политикам

3. **Использование общей системы кол-центра для банка и партнера**
   - Преимущества: отсутствие необходимости интеграции, единый источник данных
   - Недостатки: высокие затраты на миграцию, организационные сложности, проблемы с разграничением доступа

4. **Ручная передача данных о ставках в партнерский кол-центр**
   - Преимущества: отсутствие затрат на разработку интеграции
   - Недостатки: высокий риск человеческой ошибки, задержки в обновлении данных, трудоемкость процесса

### **Недостатки, ограничения, риски**
Подробно опишите здесь недостатки, ограничения и риски выбранного решения.

1. **Технические ограничения**:
   - Возможная задержка в обновлении данных в партнерском кол-центре (до 1 часа)
   - Ограниченные возможности по форматированию и представлению данных в файловом обмене
   - Зависимость от доступности SFTP-сервера для передачи данных

2. **Риски безопасности**:
   - Необходимость размещения SFTP-сервера в DMZ-сегменте с доступом из внешней сети
   - Риски компрометации учетных данных для доступа к SFTP
   - Возможные уязвимости в реализации API для системы кол-центра банка

3. **Операционные риски**:
   - Возможные сбои в автоматической выгрузке/загрузке файлов
   - Риск рассинхронизации данных между системами при сбоях
   - Сложности с диагностикой проблем при отсутствии прямой связи с партнерским кол-центром

4. **Архитектурные недостатки**:
   - Наличие двух разных механизмов интеграции для схожих задач усложняет поддержку
   - Отсутствие единого интерфейса для управления ставками во всех системах
   - Необходимость поддержки совместимости форматов при изменении структуры данных

5. **Риски масштабирования**:
   - При увеличении числа партнерских кол-центров потребуется создание отдельных учетных записей и настроек для каждого
   - Возможное увеличение нагрузки на SFTP-сервер при масштабировании
   - Ограничения пропускной способности при параллельной передаче файлов большому числу партнеров
